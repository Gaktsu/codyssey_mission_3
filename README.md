# Mini NPU Simulator

## 1. 미션 개요

### 1.1 배경

컴퓨터는 그림의 '모양'을 보지 못하고 숫자만 이해한다. 그래서 십자가(Cross)나 X 같은 패턴을 0/1(또는 실수) 2차원 배열로 바꾸고, 판별 기준이 되는 **필터**와 같은 위치끼리 곱해서 모두 더한다(**MAC**, Multiply-Accumulate). 점수가 높은 필터 쪽으로 판정한다. AI 모델은 이 MAC 연산을 수억 번 반복하고, NPU는 이를 병렬로 처리하는 전용 칩이다. 이 프로젝트는 그 원리를 Python 콘솔 프로그램으로 직접 구현한 미니 시뮬레이터다.

## 2. 핵심 기능

### 2.1 모드 1 — 사용자 입력 (3×3)

필터 A와 B, 패턴을 한 줄씩(공백 구분) 입력받는다. A 점수, B 점수, 연산 시간(10회 평균), 판정(A / B / 판정 불가)을 출력한다.

```
A 점수: 1.0
B 점수: 5.0
연산 시간(평균/10회): 0.0005 ms
판정: B
```

### 2.2 모드 2 — data.json 분석

`size_5`, `size_13`, `size_25` 필터를 불러온다. 패턴 키 `size_{N}_{idx}`에서 N을 뽑아 해당 크기의 필터를 고르고, 케이스마다 Cross 점수, X 점수, 판정, expected, PASS/FAIL을 출력한다.

```
size_5 필터 로드 완료
size_13 필터 로드 완료
size_25 필터 로드 완료
size_5_1: Cross=0.9, X=0.8999999999999999, 판정=UNDECIDED, expected=X, FAIL
size_5_2: Cross=8.9, X=0.1, 판정=Cross, expected=Cross, PASS
...
```

### 2.3 성능 분석

크기별로 MAC 연산을 10번 반복한 평균 시간(ms)과 연산 횟수(N²)를 표로 출력한다. 모드 1은 사용자가 입력한 3×3 패턴과 필터 A로 측정하고, 모드 2는 3×3 / 5×5 / 13×13 / 25×25 패턴을 패턴 생성기로 만들어 측정한다.


|크기 (N×N)|평균 시간 (ms)|연산 횟수 (N²)|
|---|---|---|
|3×3|0.0005|9|
|5×5|0.0009|25|
|13×13|0.0051|169|
|25×25|0.0176|625|


### 2.4 결과 요약

모드 2를 마치면 총 테스트 수, 통과 수, 실패 수와 실패 케이스별 사유를 출력한다.

```
총 6 / 통과 3 / 실패 3
실패 케이스:
  size_5_1: 두 점수가 동점(UNDECIDED)이라 판정 불가
  size_13_2: 두 점수가 동점(UNDECIDED)이라 판정 불가
  size_25_1: 두 점수가 동점(UNDECIDED)이라 판정 불가
```

## 3. 실행 방법

### 3.1 실행 명령

**프로젝트 루트**에서 실행한다.

```bash
python src/main.py      # Windows
python3 src/main.py     # macOS / Linux
```

### 3.2 모드 선택

```
모드를 선택하세요 (1: 사용자 입력, 2: data.json 분석):
```

- `1`: 사용자 입력 모드. 필터 A 3줄, 필터 B 3줄, 패턴 3줄을 순서대로 입력한다 (예: `0 1 0`).
- `2`: data.json 분석 모드
- 그 밖의 입력: "잘못된 선택입니다. 1 또는 2를 입력하세요." 출력 후 다시 입력받는다.
- Ctrl+C / Ctrl+D(EOF): "입력이 종료되어 프로그램을 종료합니다." 출력 후 종료한다 (트레이스백 없음).

### 3.3 data.json 위치

- 위치: `data/data.json` (프로젝트 루트 아래 `data` 폴더)
- 경로 기준: **실행한 위치(cwd) 기준** 상대 경로다. 그래서 반드시 프로젝트 루트에서 `python src/main.py`로 실행해야 한다. `src/` 안에서 실행하면 파일을 찾지 못한다.
- 파일이 없을 때: `data.json을 찾을 수 없습니다: data/data.json` 출력 후 모드 2를 종료한다.
- JSON 문법 오류일 때: `data.json 형식 오류: <상세>` 출력 후 모드 2를 종료한다.

## 5. 구현 요약

### 5.1 라벨 정규화

| 원본 | 출처 | 표준 라벨 |
|------|------|-----------|
| `+` | expected | Cross |
| `cross` | filter 키 | Cross |
| `x` | expected, filter 키 | X |

- 표에 없는 값이면 `None`을 반환, 해당 케이스는 "라벨 정규화 실패"로 FAIL 처리
- 필터를 불러온 뒤부터 출력과 PASS/FAIL 비교까지 모두 표준 라벨로만 처리한다.

### 5.2 MAC 연산

`mac.mac(pattern, filt)`는 이중 `for` 반복문으로 `pattern[i][j] * filt[i][j]`를 `total = 0.0`에 계속 더해서 float를 반환한다. 크기 검증은 호출하는 쪽(`data_loader`)에서 먼저 한다. 보너스로 `mac.make_pattern(n, label)`은 N×N Cross(가운데 행과 열) 또는 X(두 대각선) 패턴을 만든다. N=3이면 미션 예시와 같고, 성능 측정 입력으로도 쓴다.

### 5.3 동점 처리 정책 (epsilon)

`judge.decide()`는 `abs(score_a - score_b) < 1e-9`이면 동점으로 본다. 0.1처럼 이진수로 정확히 표현할 수 없는 실수를 더하다 보면 같은 값이 `0.9`와 `0.8999999999999999`처럼 미세하게 달라진다. 이런 의미 없는 차이로 승패가 갈리지 않게 하기 위해서다.

- 모드 1: `A` / `B` / `판정 불가`
- 모드 2: `Cross` / `X` / `UNDECIDED`. 판정이 expected와 같으면 PASS이고, `UNDECIDED`는 항상 FAIL이다.

### 5.4 입력 검증 및 예외 처리

- [x] 모드 1: 한 줄의 숫자 개수가 3개가 아닐 때 → "입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요." 출력 후 **그 줄만** 다시 입력받음
- [x] 모드 1: 숫자로 파싱할 수 없을 때 → 같은 안내 후 그 줄만 다시 입력받음
- [x] 모드 2: data.json이 없거나 JSON 문법 오류일 때 → 안내 후 종료 (크래시 없음)
- [x] 모드 2: 패턴 키가 `size_{N}_{idx}` 형식이 아닐 때 → 케이스 FAIL + "키 형식 오류"
- [x] 모드 2: `size_N` 필터가 없을 때 → 케이스 FAIL + "size_N 필터가 없습니다."
- [x] 모드 2: 패턴/필터 크기가 N×N이 아닐 때 → 케이스 FAIL + "크기 불일치"
- [x] 모드 2: expected가 정규화되지 않는 값일 때 → 케이스 FAIL + "라벨 정규화 실패"

FAIL이 나도 예외를 던지지 않고 결과(dict)에 사유를 담아 반환한다. 그래서 나머지 케이스는 계속 평가된다.

**출력 형식 참고:** 미션 예시의 `✓ size_5 필터 로드 완료`에서 `✓` 기호는 뺐다. Windows 기본 콘솔(cp949)에서 `✓`(U+2713)를 출력하면 `UnicodeEncodeError`로 프로그램이 종료되는 것을 확인했고, 미션에 "문구와 디자인은 달라도 된다"고 되어 있기 때문이다.

## 6. 결과 리포트

> 케이스별 상세 표, 오류 입력 검증, 크기별 측정 원자료: [docs/report.md](docs/report.md)

### 6.1 실패 원인 분석

data.json 6개 케이스 중 **통과 3 / 실패 3**이다. FAIL은 size_5_1, size_13_2, size_25_1이고, 세 건 모두 원인이 같다.

1. **데이터/스키마 문제가 아니다.** 세 케이스 모두 키 파싱, 필터 선택, N×N 크기 검증, 라벨 정규화(`x`→X, `+`→Cross)를 통과해서 MAC 계산까지 진행됐다. 스키마 문제였다면 "키 형식 오류", "크기 불일치" 같은 별도 사유가 나왔을 것이다.
2. **로직 문제가 아니다.** MAC과 판정 로직은 3×3 예시(십자가×십자가=5.0, 십자가×X=1.0)와 PASS 3건에서 올바르게 동작했다.
3. **수치 비교(동점 정책) 때문에 FAIL이 났다.** 점수 쌍은 0.9 vs 0.8999999999999999, 7.499999999999997 vs 7.5, 4.9 vs 4.899999999999999다. `fractions.Fraction`으로 정확하게 다시 계산하면 세 쌍 모두 **수학적으로 같은 값**(0.9, 7.5, 4.9)이다. 차이는 실수를 누적해서 더하면서 생긴 부동소수점 오차(약 1e-15)뿐이다.
4. 그래서 epsilon(1e-9) 정책에 따라 `UNDECIDED`로 판정됐고, 규칙상 `UNDECIDED`는 FAIL이다. 만약 epsilon 없이 `>`로 바로 비교했다면 의미 없는 오차가 승자를 정했을 것이고, 세 건 모두 expected와 반대로 판정됐을 것이다(size_5_1·size_25_1은 Cross, size_13_2는 X).
5. 결론적으로 이 FAIL은 버그가 아니라 **"근거 없이 판정하지 않는다"는 정책이 의도대로 동작한 결과**다. PASS를 만들려면 계산 방식이 아니라 데이터(동점 패턴의 expected 재정의)나 정책(tie-break 규칙)을 바꿔야 한다.
6. PASS 3건이 PASS로 나온 것은 **라벨 정규화** 덕분이다. 정규화가 없으면 expected `'x'`와 판정 `'X'`, expected `'+'`와 필터 키 `'cross'`가 맞지 않아서 6건이 모두 FAIL이 된다.

### 6.2 시간 복잡도 분석 (O(N²))

| 크기 (N×N) | 평균 시간 (ms, 10회) | 연산 횟수 (N²) | 칸당 시간 (ns) |
|------------|----------------------|----------------|----------------|
| 3×3   | 0.0005 | 9   | 약 56 |
| 5×5   | 0.0009 | 25  | 약 36 |
| 13×13 | 0.0051 | 169 | 약 30 |
| 25×25 | 0.0180 | 625 | 약 29 |

1. `mac()`은 N번 도는 반복문 안에 N번 도는 반복문이 있다. 칸마다 곱셈 1번과 덧셈 1번을 하므로 연산 횟수는 정확히 N²이고, 시간 복잡도는 **O(N²)**이다.
2. 측정 구간은 `mac()` 호출 10회뿐이다(`time.perf_counter`). 파일 읽기, 입출력, 패턴 생성은 측정에서 뺐다.
3. 5×5 → 25×25에서 N은 5배, 연산 횟수는 25배(25 → 625)인데, 시간은 약 20배(0.0009 → 0.0180) 늘었다. 시간이 N이 아니라 N²을 따라간다.
4. 칸당 시간(평균 시간 ÷ N²)은 N이 커질수록 약 29~30ns로 거의 일정해진다. "칸 하나의 비용은 일정하고, 칸의 개수가 N²개"라는 O(N²)의 정의를 측정값으로 확인할 수 있다.
5. 작은 크기에서 칸당 비용이 높게 나오는 것(3×3: 약 56ns)은, 함수 호출·반복문 준비처럼 크기와 상관없이 매번 드는 고정 비용이 전체 시간에서 차지하는 비중이 크기 때문이다. N이 커지면 고정 비용의 비중이 작아져서 시간이 N²에 비례하는 모습이 더 뚜렷해진다.
6. 측정값은 실행할 때마다 ±10% 정도 달라지지만 크기별 비율은 매번 비슷하게 나왔다(3번 측정).
7. N이 10배가 되면 연산은 100배가 된다. 실제 AI 모델의 필터는 수백×수백 크기이고 수천 개라서, 칸끼리 서로 독립적인 MAC을 병렬로 처리하는 NPU가 필요한 이유가 여기에 있다.
