측정 환경: Windows 11, Python 3.12.10, 프로젝트 루트에서 `python src/main.py` 실행 (모드 2).

## 2. 실패 원인 분석

실패 원인은 세 가지로 나눠서 진단했다.

| 분류 | 의미 | 이 프로젝트에서 잡아내는 위치 |
|------|------|------------------------------|
| 데이터/스키마 | 키 형식, 필터 누락, 크기 불일치, 라벨 표기 | `data_loader.evaluate_pattern()`이 사유별로 FAIL 처리 |
| 로직 | MAC 계산, 판정 함수 자체의 오류 | 3×3 예시(십자가×십자가=5, 십자가×X=1)로 검증 |
| 수치 비교 | 로직과 데이터는 정상인데 두 점수가 epsilon 안으로 붙음 | `judge.decide()`가 UNDECIDED 반환 → FAIL |

실제 FAIL 3건은 모두 **수치 비교** 유형이다.

### 2.1 size_5_1, size_13_2, size_25_1 (공통 원인)

- 현상: Cross 점수와 X 점수의 차이가 1e-9보다 작아서 `UNDECIDED`가 나왔다. `UNDECIDED`는 expected와 상관없이 FAIL로 처리된다.
- 원인 분류: **수치 비교 (동점 정책)**. 데이터/스키마 문제나 로직 문제가 아니다.
- 근거:
  1. 데이터/스키마는 정상이다. 키에서 N을 추출했고, `size_N` 필터를 찾았고, N×N 크기 검증과 라벨 정규화(`x`→X, `+`→Cross)도 모두 통과해서 MAC 계산까지 진행됐다. 앞 단계에서 걸렸다면 사유가 "키 형식 오류", "크기 불일치" 같은 문구로 나온다.
  2. 두 점수는 수학적으로 **완전히 같다**. 입력값을 `fractions.Fraction`(정확한 분수 계산)으로 다시 계산해 보면 size_5_1은 0.9 = 0.9, size_13_2는 7.5 = 7.5, size_25_1은 4.9 = 4.9로 정확히 일치한다.
  3. `0.8999999999999999`나 `7.499999999999997` 같은 값은 0.1처럼 이진수로 정확히 표현할 수 없는 실수를 여러 번 더하면서 생긴 **부동소수점 누적 오차**다. 더하는 순서와 값이 필터마다 달라서 오차 크기도 달라진다.
  4. epsilon을 쓰지 않고 `>`로 바로 비교했다면 size_5_1과 size_25_1은 우연히 Cross 승(FAIL), size_13_2는 X 승(FAIL)으로 판정됐을 것이다. 의미 없는 1e-15 수준의 차이가 승부를 정하게 된다.
- 결론: 동점 정책이 **의도대로 동작한 결과**다. data.json의 expected는 X나 Cross 중 하나를 요구하지만, 두 필터와의 유사도가 정확히 같은 패턴은 어느 쪽으로도 판정할 근거가 없다. 그래서 "판정 불가"가 올바른 출력이다.
- 개선 방안 (필요한 경우):
  - 데이터 쪽: 동점 패턴의 expected를 "UNDECIDED 허용"으로 정의하거나, 동점이 아닌 패턴으로 교체한다.
  - 정책 쪽: 동점일 때 우선 라벨을 정하는 규칙(tie-break)을 추가할 수 있다. 다만 근거 없는 판정이 되므로 이 프로젝트에서는 적용하지 않았다.
  - 계산 쪽: `decimal`/`fractions`로 정확하게 계산하면 오차는 없어지지만, 점수가 정확히 같다는 사실은 그대로라서 결과는 똑같이 UNDECIDED다. 결국 바꿔야 하는 것은 계산 방식이 아니라 데이터나 정책이다.

### 2.2 데이터/스키마 오류 처리 확인 (의도적 오류 입력)

현재 data.json에는 스키마 오류가 없다. 그래서 `evaluate_pattern()`에 일부러 잘못된 입력을 넣어서 케이스 단위 FAIL이 되는지 확인했다. 어떤 경우에도 프로그램은 멈추지 않고 다음 케이스로 넘어간다.

| 오류 입력 | 출력된 실패 사유 |
|-----------|------------------|
| 키 `bad_key` | 키 형식 오류: 'bad_key'는 size_{N}_{idx} 형식이 아닙니다. |
| 키 `size_7_1` (필터 없음) | size_7 필터가 없습니다. |
| 키 `size_13_9` + 5×5 입력 | 크기 불일치: 패턴/필터가 13×13이 아닙니다. |
| expected `'o'` | 라벨 정규화 실패: expected='o' |
| data.json 없음 | data.json을 찾을 수 없습니다: data/data.json (종료, 트레이스백 없음) |

라벨 정규화를 하지 않았다면 expected `'x'`와 판정 `'X'`, expected `'+'`와 필터 키 `'cross'`가 서로 맞지 않는다. 그러면 PASS 3건까지 모두 FAIL이 된다. 정규화 덕분에 PASS 3건이 정상적으로 PASS로 나온다.

## 3. 성능 분석

### 3.1 측정 방법

- 함수: `perf.measure_avg_ms()`. `time.perf_counter()`로 `mac()` 호출을 10회 반복한 구간만 재고, 10으로 나눈 평균을 ms로 출력한다.
- 입력: 크기마다 B1 생성기(`make_pattern`)로 만든 Cross 패턴과 Cross 필터를 쓴다. 크기별로 같은 조건에서 비교하기 위해서이고, data.json에는 3×3이 없기 때문이기도 하다.
- 제외 구간: 파일 읽기, 콘솔 입출력, 패턴 생성은 측정 구간 밖에서 처리한다.

### 3.2 측정 결과

같은 환경에서 3번 측정한 값이다. 실행할 때마다 ±10% 정도 차이가 난다.

| 크기 (N×N) | 평균 시간 (ms) | 연산 횟수 (N²) | 1회 곱셈·덧셈당 시간 (ns) |
|------------|----------------|----------------|---------------------------|
| 3×3   | 0.0005 | 9   | 약 56 |
| 5×5   | 0.0009 | 25  | 약 36 |
| 13×13 | 0.0051 | 169 | 약 30 |
| 25×25 | 0.0180 | 625 | 약 29 |

### 3.3 시간 복잡도 분석 (O(N²))

- `mac()`은 `for i in range(n)` 안에 `for j in range(n)`이 있는 이중 반복문이다. 칸마다 곱셈 1번과 덧셈 1번을 한다. 그래서 연산 횟수는 정확히 N×N = N²이고, 시간 복잡도는 **O(N²)**이다.
- 측정값과 비교하면 5×5 → 25×25에서 연산 횟수는 25배(25 → 625), 시간은 약 20배(0.0009 → 0.0180)다. 5×5 → 13×13은 연산 횟수 6.8배, 시간 약 5.7배다. 시간은 N이 아니라 N²에 비례해서 늘어난다.
- 마지막 열(시간 ÷ N²)을 보면 크기가 커질수록 약 29~30ns로 수렴한다. "칸 하나를 처리하는 비용이 일정하고, 칸의 개수가 N²개"라는 O(N²)의 정의가 측정값으로 확인된다.
- 작은 크기에서 칸당 비용이 높게 나오는 것(3×3: 약 56ns)은, 함수 호출·반복문 준비·`perf_counter` 호출처럼 크기와 상관없이 매번 드는 **고정 비용**이 전체 시간에서 차지하는 비중이 크기 때문이다. N이 커지면 고정 비용의 비중이 작아져서 시간이 N²에 비례하는 모습이 더 뚜렷해진다.
- 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 쓴다. N이 10배가 되면 연산은 100배가 된다. 이렇게 서로 독립적인 곱셈을 순서대로 처리하는 대신 동시에 처리하려고 만든 것이 NPU다.
