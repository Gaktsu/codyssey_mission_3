# 미션 Q&A

## 1. 이 미션의 목적은 패턴 자리를 비교해 일치율을 확인하는 것인가?

거의 맞지만, 핵심은 **"일치율"이 아니라 "어느 필터와 더 비슷한가"를 고르는 분류**다.

- 필터 2개(Cross, X)를 각각 입력 패턴과 MAC 연산해서 점수를 낸다.
- **점수가 더 높은 필터 쪽으로 판정**한다.
- 점수 하나만 보고 "몇 % 일치"를 따지지 않고, 두 점수를 서로 비교한다.

## 2. MAC 연산이란? 행렬 연산인가?

**같은 위치끼리 곱하고(Multiply) 전부 더하는(Accumulate) 연산**이다.

```
점수 = Σ 패턴[i][j] × 필터[i][j]
```

- 행렬 곱셈 자체는 아니다. 다만 행렬 곱셈과 CNN 합성곱을 이루는 **가장 작은 연산 단위**다.
- 두 행렬을 1줄로 펴서 벡터 내적을 한 것과 같다.
- NPU는 이 연산을 수천 개씩 동시에 처리하는 칩이다.

## 3. 모드는 왜 1, 2로 나뉘는가?

| | 모드 1 | 모드 2 |
|---|---|---|
| 목적 | 원리 확인 (손으로 검산 가능) | 일괄 검증 + 크기별 성능 |
| 크기 | 3×3 | 5×5, 13×13, 25×25 |
| 라벨 | A / B (사용자 필터) | Cross / X (정규화 필요) |
| 정답 비교 | 없음 | expected와 비교해 PASS/FAIL |

- **모드 1**: MAC 연산이 맞게 동작하는지 사람이 직접 확인하는 단계.
- **모드 2**: 실제 데이터를 다룰 때 생기는 문제(라벨 형식, 스키마, 부동소수점, 성능)를 다루는 단계.

## 4. 판정 불가는 어떤 경우에 발생하는가?

**두 점수의 차이가 1e-9보다 작을 때** 발생한다. 모드 1에서는 "판정 불가", 모드 2에서는 `UNDECIDED`로 표시한다.

- 실제 data.json에도 이런 케이스가 있다.
- 예: `size_5_1`은 Cross 점수 `0.9`, X 점수 `0.8999999999999999`.
- 확인 결과 6개 케이스 중 3개가 이렇게 거의 같은 점수였다.

## 5. data.json은 어떻게 되어 있는가? 패턴이 들어 있는가?

```
{
  "meta": {...},
  "filters": {
    "size_5":  { "cross": [[...]], "x": [[...]] },
    "size_13": {...}, "size_25": {...}
  },
  "patterns": {
    "size_5_1": { "input": [[...5×5...]], "expected": "x" },
    "size_5_2": { "input": [...], "expected": "+" },
    ...  (총 6개: 크기별 2개)
  }
}
```

- 패턴과 **필터가 함께 들어 있다.**
- 값은 0과 1만 있는 게 아니라 `0.9`, `0.1`, `7.5` 같은 실수도 섞여 있다.

## 6. 크기 불일치 검증은 복사본을 만들어 값을 수정한 뒤 테스트해야 하는가?

그렇다. 원본에는 크기가 어긋난 케이스가 없어서, 그대로 두면 검증 코드가 한 번도 실행되지 않는다.

- **원본은 수정하지 않는다.** 채점 기준 데이터이기 때문이다.
- 방법은 둘 중 하나다.
  - 복사본(예: `data/invalid_size.json`)을 만들어 한 행을 지운 뒤 실행한다.
  - 테스트 코드 안에서 원본을 읽고 메모리에서만 일부를 망가뜨려 검증한다.

## 7. 라벨 정규화는 어떻게 하는가?

여러 형태로 적힌 라벨을 **프로그램 안에서 쓰는 이름 2개로 통일**한다.

```python
{"+": "Cross", "cross": "Cross", "x": "X"}
```

- expected는 `'+'`와 `'x'`, 필터 키는 `'cross'`와 `'x'`로 표기가 서로 다르다.
- 정규화하지 않으면 `'+' == 'cross'`가 False가 되어, 정답이어도 FAIL이 난다.
- 이것이 미션이 말하는 "라벨/스키마 문제"의 대표 예다.

## 8. 점수는 "맞춘 개수 / 자리 개수" 같은 퍼센트인가?

**아니다.** 나누지 않고 **곱한 값을 더한 원래 합계 그대로**가 점수다.

- 값이 0과 1뿐이면 점수는 "패턴과 필터가 **둘 다 1인 칸의 개수**"가 된다.
- 둘 다 0인 칸은 점수에 들어가지 않으므로 "맞춘 개수"와는 다르다.
  - 예: 십자가 × 십자가 필터 = 5 (9칸이 전부 일치해도 점수는 5)
- 값이 실수이면 가중치처럼 작동한다 (예: 0.9 × 1 = 0.9).
- 판정은 두 점수의 크기만 비교하므로 퍼센트로 바꿀 필요가 없다.

## 9. 허용 오차는 왜 넣는가? 동점을 정하기 위해서인가?

동점 판정을 위한 것이기도 하지만, 본질은 **계산 오차 때문에 승자가 잘못 정해지는 것을 막기 위해서**다.

- 컴퓨터는 0.1 같은 실수를 정확히 저장하지 못한다. 그래서 `0.1 + 0.2 == 0.3`이 False다.
- 수학적으로는 둘 다 0.9인 값이 계산 과정에서 `0.9`와 `0.8999999999999999`로 갈릴 수 있다.
- epsilon 없이 `>`로 비교하면 이 오차만으로 Cross가 이긴 것으로 판정된다.
- epsilon은 "이 정도 차이는 같은 값으로 본다"는 기준선이다.

## 10. expected는 점수가 설정값보다 높으면 PASS인 것인가?

**아니다.** expected는 점수가 아니라 **정답 라벨**(`'+'` 또는 `'x'`)이다.

```
판정 라벨 == 정규화된 expected  → PASS
그 외 (UNDECIDED 포함)          → FAIL
```

점수 임계값 같은 것은 없다.

## 11. 보너스 과제는 하는가?

선택 사항이다. 판단 기준:

- **B1 패턴 생성기는 추천한다.** 성능 분석에서 3×3 측정용 패턴이 필요한데 data.json에는 3×3이 없다. 생성기가 있으면 이 문제가 해결되고, 코드도 몇 줄이면 된다.
- **B2 1차원 최적화는 여유가 있을 때 한다.** 앞의 기능들이 끝난 뒤 성능 비교 표 하나를 추가하는 정도다.
