  테스트 코드 자체는 제출 대상이 아니므로(.gitignore로 제외) 본인 검증용으로만 사용.

  - A와 패턴을 동일하게 입력 → "판정 불가" 출력 확인.
  - 한 줄에 숫자 2개(`1 0`)나 파싱 불가 값(`1 a 1`)을 일부러 입력 → 안내 문구 후 그 줄만 재입력되는지 확인.
- `python3 src/main.py` 를 루트에서 실행(모드 2):

## 2. 미션 원문(mission_context.md)과 구현이 다른 부분 — 평가 때 질문 나올 수 있음

- **`✓` 기호 생략**: mission_context.md의 예시 출력은 `✓ size_5 필터 로드 완료`처럼 체크마크가 있지만,
  구현에서는 뺐음. 이유: Windows 기본 콘솔(cp949)에서 `✓`(U+2713)를 출력하면 `UnicodeEncodeError`로
  프로그램이 죽는 걸 직접 재현해서 확인했고, 미션 원문에 "실제 문구와 디자인은 달라도 된다"는 문구가 있어
  의도적으로 제외함. README에 한 줄로 이유를 적어두는 걸 권장.
- **결과 요약 한 줄 출력**: 미션 예시는 "총 테스트/통과/실패"를 3줄로 나눠 보여주지만, 구현은
  `총 N / 통과 N / 실패 N` 한 줄로 합침. 포맷 자유 범위 안이라 문제는 없지만 README에 실제 출력 예시를
  캡처해서 보여주는 걸 권장.
- **모드 1 성능 출력이 "표"가 아니라 한 줄 숫자**: features.md의 F6 요구사항은 "연산 시간(평균/10회) 출력"만
  요구해서 `연산 시간(평균/10회): 0.0035 ms` 형태의 한 줄로 구현함. 다만 mission_context.md 실행 흐름에는
  "성능 분석(3×3) 출력"이라고만 적혀 있고 표 형식을 명시하진 않음 — 현재 구현대로 충분하다고 판단되지만,
  채점 기준이 "표 형식 통일"을 요구한다면 모드 1도 1행짜리 표로 바꿔야 할 수 있음(현재 코드엔 없음).

## 5. 평가 때 설명할 수 있어야 하는 핵심 개념 (mission_context.md 3절 기준)

### 5.1 MAC(Multiply-Accumulate) 연산과 AI에서의 중요성
같은 위치의 값끼리 곱한 뒤 전부 더하는 연산(`mac.py`의 `mac()`). 행렬 곱셈 자체는 아니지만, 행렬 곱셈과
CNN의 합성곱(convolution)을 이루는 가장 작은 연산 단위다. 실제 AI 모델은 큰 필터를 수천 개씩 적용하므로
수억 번의 MAC이 필요하고, 이걸 동시에(병렬로) 처리하려고 NPU라는 전용 칩이 만들어졌다 —
이 미션은 그 연산 1개를 반복문으로 직접 구현해보는 것.

### 5.2 패턴·필터 유사도 계산 원리
"몇 % 일치"가 아니라 **Cross 필터 점수와 X 필터 점수 중 어느 쪽이 더 높은가**로 분류한다. 값이 0/1뿐이면
점수는 "패턴과 필터가 둘 다 1인 칸의 수"가 되고(예: 십자가×십자가=5), 둘 다 0인 칸은 점수에 안 잡힌다.
실수 값(0.9, 7.5 등)이 섞이면 가중치처럼 작동한다. `judge.py`의 `decide()`가 두 점수를 비교해 라벨을 고른다.

### 5.3 라벨 정규화가 필요한 이유
data.json에서 정답(`expected`)은 `'+'`/`'x'`로, 필터 키는 `'cross'`/`'x'`로 서로 다른 표기를 쓴다.
정규화 없이 `'+' == 'cross'`를 비교하면 항상 False가 되어 정답이어도 FAIL이 난다. `judge.py`의
`normalize_label()`이 이 두 표기를 표준 라벨(`Cross`/`X`) 하나로 통일해서, 이후 모든 비교가 표준 라벨
기준으로만 이뤄지게 한다.

### 5.4 부동소수점 오차와 epsilon 기반 비교
컴퓨터는 0.1 같은 실수를 정확히 저장하지 못한다(`0.1 + 0.2 == 0.3`이 `False`인 것과 같은 문제). 수학적으로
같은 값이 연산 과정에서 `0.9`와 `0.8999999999999999`처럼 미세하게 달라질 수 있는데, 이 미세한 차이만으로
승자가 잘못 정해지는 걸 막으려고 `abs(a - b) < 1e-9`이면 동점(UNDECIDED)으로 처리한다(`judge.py`의
`EPSILON`, `decide()`). 실제 data.json 6개 케이스 중 3개가 이 경계에 걸려 UNDECIDED가 나왔다(4절 표 참고).

### 5.5 시간 복잡도 O(N²)
MAC 연산은 N×N 행렬의 모든 칸을 한 번씩 곱하고 더하므로 연산 횟수가 정확히 N²이다(`perf.py`의
`measure_sizes()`가 반환하는 세 번째 값). 로컬에서 측정한 예시 결과:

| 크기 | 연산 횟수(N²) | 평균 시간(ms, 참고용) |
|---|---|---|
| 3×3 | 9 | 0.0035 |
| 5×5 | 25 | 0.0044 |
| 13×13 | 169 | 0.0178 |
| 25×25 | 625 | 0.0678 |

5×5 → 25×25는 연산 횟수가 25배(25→625)인데, 측정 시간도 대략 비슷한 배수로 늘어난다(작은 크기일수록
Python 함수 호출 오버헤드 비중이 커서 비율이 정확히 들어맞지는 않음 — N이 커질수록 N² 경향이 더
뚜렷해진다는 점을 README에서 언급하면 좋음). 실제 제출 시엔 본인 환경에서 재측정한 수치를 쓸 것
(측정값은 머신·실행마다 달라짐).

### 5.6 실패 원인 분류: 데이터/스키마 vs 로직 vs 수치 비교
- **데이터/스키마 문제**: 키가 `size_{N}_{idx}` 형식이 아니거나, 필요한 `size_N` 필터가 없거나, 패턴/필터
  크기가 N×N이 아니거나, expected 라벨을 정규화할 수 없는 경우. `data_loader.py`의 `evaluate_pattern()`이
  이 네 가지를 각각 구분된 사유 문자열로 FAIL 처리한다.
- **로직 문제**: MAC 계산이나 판정 함수 자체가 잘못된 경우 (이 프로젝트에선 단위 테스트 49개로 검증됨).
- **수치 비교 문제**: 로직·데이터 모두 정상이지만 두 점수가 epsilon 이내로 가까워 UNDECIDED가 나고,
  UNDECIDED는 정의상 FAIL인 경우. 실제 data.json의 FAIL 3건은 전부 이 세 번째 유형이다 — "버그가 아니라
  설계된 동작"이라는 걸 구분해서 설명할 수 있어야 한다.
